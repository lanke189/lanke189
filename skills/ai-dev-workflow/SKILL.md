# AI 软件开发工作流

将 [流程规范](references/AI软件开发流程规范.md) 作为原则依据。启动时先读项目已有 `AGENTS.md`、仓库和 `docs/开发进度.md`；如果没有进度文件，则判断当前阶段并建立记录。不要重复已经完成且仍有效的工作。

## 运行规则

1. 先弄清目标、现有系统、项目规模和风险。只询问会影响方向或结果的缺失信息；其他内容写成假设。按风险选择轻量、标准或增强流程。轻量项目可以合并文档，不得省略范围、验收条件、关键安全验证和变更记录。没有界面的项目将 UI 阶段标记为“不适用”，说明原因。
2. 以 `docs/开发进度.md` 为阶段状态的唯一项目内索引。使用 [开发进度模板](assets/开发进度模板.md) 记录项目档位、当前阶段、每阶段状态、交付物路径、批准人/批准日期或批准依据、待确认事项、下一步。状态使用 `未开始 / 进行中 / 待确认 / 已批准 / 已完成 / 阻塞 / 不适用`。文档和代码是事实依据；状态与实际冲突时先纠正状态。
3. 阶段顺序：需求 → UI → 技术方案与 API 契约 → 开发 → 联调验收 → 发布。使用 `assets/` 中的模板生成项目文档，按项目裁剪空项。不要仅为满足目录结构创建空文件。
4. 需求、UI、技术方案分别形成可审查交付物后进入 `待确认`，向用户呈现关键决策和待确认问题。只有用户明确批准或项目中存在可核实的既有批准记录，才将其标为 `已批准` 并进入下一阶段。审批具体方案，不把沉默、AI 自检或含糊回应算作批准。用户已经明确授权并确认的内容，无需重复询问。
5. 已批准的范围内自主完成开发、验证和修复。验收结果由用户或指定负责人确认；发布、上线、合并等外部或难以回退的操作依当前授权执行，未获授权时先准备可审查结果。若出现实质需求变化、UI 行为变化、API 破坏性变化或重大技术选型变化，更新受影响文档与状态，再确认变更；纯视觉或局部实现调整按影响范围处理。

## 各阶段最低要求

| 阶段 | 主要产物 | 通过依据 |
| --- | --- | --- |
| 需求 | [需求方案模板](assets/需求方案模板.md) | 目标、范围、业务规则、异常场景和可验证验收条件明确 |
| UI | UI 稿及 [UI方案模板](assets/UI方案模板.md) | 页面、交互、空/加载/错误/权限状态与需求一致；无 UI 时记录不适用 |
| 技术 | 开源/现有能力调研、[技术方案模板](assets/技术方案模板.md)、适用时 [API契约模板](assets/API契约模板.md) | 选型、前后端边界、数据、安全、验证方法清楚；有 API 时双方契约一致 |
| 开发 | 可验证的功能切片、代码与测试记录 | 在批准范围内实现；每片完成相关验证，记录剩余问题 |
| 联调验收 | [验收清单模板](assets/验收清单模板.md) | 关键路径、异常、回归和风险对应的安全检查有结果；阻断问题处理 |
| 发布 | 发布说明、版本/提交、回滚方式 | 负责人确认发布决定，发布后关键路径验证并记录结果 |

## 贯穿检查

- 技术方案定稿前先检查现有代码和适合的开源项目/组件；核查许可证、维护情况、适用性及已知安全风险。无法联网时记录限制，不编造调研结果。
- 优先复用现有结构和成熟能力，先实现最小功能闭环。新增框架、抽象层、配置系统或基础设施时说明它解决的当前问题及更简单方案为何不足。
- API 契约在前后端并行开发前明确字段、状态、错误和权限；变更先同步契约。纯前端或无 API 项目注明不适用。
- 修改前检查 `git status`、相关文件和影响范围；尊重用户已有未提交改动。检查 `.gitignore` 与密钥暴露，保留可回退基线。按功能切片做必要测试和回归；记录测试命令、结果及未测风险。不要为流程需要擅自提交、合并或发布。
- 安全检查与风险匹配，至少覆盖适用的输入校验、身份认证、权限控制、错误处理、敏感信息保护和依赖风险。高风险项目增加专门评审。
- 需要项目长期约束时，从 [AGENTS.md 示例](assets/AGENTS.md.example) 改写为项目实际规则；示例不得原样覆盖已有 `AGENTS.md`。

每次工作结束更新进度文件，并向用户说明当前阶段、已完成产物、验证结果、待批准事项和下一步。详细条款按需查阅参考规范对应章节。
