# AI 软件开发流程规范

> 版本：V1.0  
> 更新日期：2026-10-30  
> 适用对象：使用 Codex、Cursor、Claude Code 等 AI 编程工具开展软件开发的个人及小团队  
> 核心目标：**让 AI 按照已确认的需求、UI 与技术方案完成可验证的最小功能闭环，而非无限扩展设计。**

---

## 一、规范目标与核心原则

### 1.1 规范目标

建立从需求讨论、UI 设计、技术选型、前后端开发到联调发布的标准工作流，减少 AI 开发中的需求偏移、UI 修改误伤业务逻辑、重复造轮子、过度设计、接口不一致和回归缺陷。

### 1.2 六项核心原则

1. **需求先行，文档约束**：在编码前明确问题、范围、业务规则和验收标准；AI 不得把推测当作已确认需求。
2. **UI 定稿，职责分离**：通过 UI 方案文档固定页面结构、交互及状态；视觉变更不应擅自触发业务逻辑变更。
3. **成熟方案优先**：技术定稿前调研 GitHub 等开源资源及项目现有组件，验证适用性、许可证、安全性和维护情况，再决定复用还是自研。
4. **契约先行，并行开发**：前后端在接口、字段、状态、错误处理等契约一致后并行开发，最终进行联调。
5. **最小必要实现**：优先完成当前 MVP 功能闭环，避免为假设中的未来需求增加不必要的抽象、架构和配置能力。
6. **小步交付，持续验证**：按独立功能单元开发、测试和提交代码；保留必要的安全措施、回归测试与回滚能力。

> 原则说明：**最小实现不等于省略安全、测试或异常处理。** 应减少非必要复杂度，但不可跳过与当前功能风险相匹配的基本保障。

---

## 二、适用范围与流程裁剪

| 项目类型 | 适用流程 | 建议产物 |
| --- | --- | --- |
| Demo / 一次性小工具 | 需求简述 → 简版 UI → 实现 → 验收 | 一页需求、关键页面、验证清单 |
| MVP / 中小型应用 | 需求 → UI → 简版技术方案 → 分模块开发 → 联调发布 | 需求文档、UI 文档、技术文档、验收清单 |
| 多模块 / 多角色业务系统 | 全流程 + API 契约 + 前后端并行 + 自动化回归 + 变更管理 | 完整阶段文档、接口契约、测试报告、发布记录 |

按项目风险而不是代码行数决定流程强度：涉及身份认证、用户隐私、支付、外部平台接口或重要业务数据时，即使是小项目，也必须补齐相应的安全和异常验证。

## 三、整体工作流与阶段门禁

```text
需求讨论与范围确认
        ↓ 〔需求评审通过〕
UI 原型与交互确认
        ↓ 〔UI 评审通过〕
开源调研与技术方案设计
        ↓ 〔技术选型、API 契约确认〕
     ┌───────────┴───────────┐
     ↓                       ↓
  前端开发                 后端开发
  Mock 验证                接口/单元测试
     └───────────┬───────────┘
                 ↓
          前后端联调
                 ↓
     功能验收、回归与安全检查
                 ↓
          发布、记录与迭代
```

| 阶段       | 必要输入            | 主要输出               | 进入下一阶段的条件      |
| -------- | --------------- | ------------------ | -------------- |
| 1. 需求设计  | 想法、场景、约束        | 需求方案文档             | 范围、规则、验收标准明确   |
| 2. UI 设计 | 已确认需求           | UI 稿、UI 方案文档       | 页面、交互、状态和异常态确认 |
| 3. 技术设计  | 需求文档、UI 文档、现有仓库 | 开源调研记录、技术方案、API 契约 | 核心选型可行、前后端契约一致 |
| 4. 并行开发  | 技术方案、任务拆分、接口契约  | 前端代码、后端代码、测试       | 独立模块已验证、代码可合并  |
| 5. 集成验收  | 集成版本、验收用例       | 联调结果、测试记录、缺陷清单     | 阻断性问题清零、关键场景通过 |
| 6. 发布迭代  | 验收版本、发布说明       | 版本发布记录、回滚方案、迭代清单   | 发布验证完成、问题可追溯   |

**阶段门禁规则**：若需求、UI、技术方案之间存在实质冲突，不应直接让 AI 猜测并继续写代码；先确认差异，再更新对应文档。

## 四、阶段 1：需求设计规范

### 4.1 目标

先与 AI 充分讨论需求，形成可被设计、开发和测试共同理解的需求方案，避免“描述一句话就开始写代码”。

### 4.2 执行动作

1. 描述目标用户、使用场景、目前的问题及希望达成的效果。
2. 拆分核心流程、角色、输入输出、业务规则及边界条件。
3. 区分 **本期必须实现**、**暂不实现**、**待确认**，禁止 AI 自行补充超范围功能。
4. 定义功能验收标准，覆盖主流程、关键异常和边界情况。
5. 与 AI 逐项评审并确认后，将版本固定为当前开发基线。

### 4.3 《需求方案.md》建议结构

```markdown
# 需求方案
## 1. 背景与问题
## 2. 目标与成功标准
## 3. 目标用户及使用场景
## 4. 本期范围 / 非本期范围
## 5. 核心业务流程
## 6. 功能清单与优先级
## 7. 业务规则及状态流转
## 8. 异常与边界场景
## 9. 数据、权限及外部依赖
## 10. 验收标准
## 11. 待确认问题 / 变更记录
```

### 4.4 验收条件示例

使用 `Given / When / Then` 描述可执行的行为，而不是“页面正常”“功能可用”之类的模糊描述。

```text
Given 用户已登录且有编辑权限
When 用户提交合法内容
Then 系统保存成功，并在页面显示最新数据

Given 用户无编辑权限
When 用户尝试提交修改
Then 后端拒绝操作，前端给出明确提示，原数据不变
```

**完成标准**：功能边界已锁定，关键规则可判定，至少能列出主路径、失败路径和权限边界的验收用例。

## 五、阶段 2：UI 设计规范

### 5.1 目标

基于已确认需求生成 UI 原型，通过多轮讨论确定界面，随后沉淀 UI 方案文档。UI 文档既是前端实现依据，也是后续局部修改时的影响边界。

### 5.2 执行动作

1. 让 AI 基于需求方案产出页面结构及主要交互，先验证信息架构和流程，再优化视觉。
2. 逐页确认展示字段、用户操作、校验规则、组件状态和页面跳转。
3. 明确加载中、空数据、提交中、成功、失败、无权限等状态。
4. UI 最终确认后，将截图、原型链接或页面描述与规则一并写入《UI方案.md》。
5. 任何后续 UI 修改先做影响分析：仅样式变动、交互变动，还是业务规则变动。

### 5.3 《UI方案.md》建议结构

```markdown
# UI 方案
## 1. 页面清单与导航结构
## 2. 页面布局与组件说明
## 3. 字段展示、编辑与校验规则
## 4. 用户操作及交互流程
## 5. 页面与组件状态（空/加载/成功/失败/无权限）
## 6. 提示文案与错误反馈
## 7. 响应式及适配要求（如需）
## 8. 与业务规则、接口的关联
## 9. 已确认 UI 基线与变更记录
```

### 5.4 UI 变更约束

| 变更类型 | 处理规则 |
| --- | --- |
| 颜色、间距、样式、纯布局 | 更新 UI 文档及受影响的前端实现，原则上不修改业务逻辑或后端 |
| 交互流程、输入项、展示规则 | 评估对业务规则、API 和测试的影响；必要时同步更新相关文档 |
| 状态流转、权限、数据定义 | 先更新并确认需求文档，再更新 UI、技术方案及测试用例 |

**完成标准**：每个核心页面均有明确的结构、交互与状态说明；AI 无需自行猜测用户如何操作或异常时展示什么。

## 六、阶段 3：开源调研与技术方案规范

### 6.1 先调研，再选型

技术方案定稿前，要求 AI 首先检查当前项目仓库和依赖，再检索 GitHub 等来源中的相似项目、现成组件或成熟 SDK。

重点评估：

- **功能匹配**：能否覆盖当前需要的能力，是否有不适用的限制。
- **维护状态**：最近维护记录、Issue/PR 处理情况、版本稳定性。
- **许可证**：是否允许当前商业使用、修改和分发，是否需要保留声明或履行开源义务。
- **安全风险**：已知漏洞、依赖风险、敏感权限、是否存在不安全默认配置。
- **集成成本**：技术栈兼容性、学习成本、二次开发成本及锁定风险。

调研结果需要记录**真实仓库地址、版本、许可证、评估结论和选择理由**。不能仅依据 AI 的口头描述把未验证的项目当作可用依赖。

### 6.2 方案制定顺序

1. 明确部署环境、技术栈、现有代码、性能要求及不可变更约束。
2. 评估复用既有代码、第三方组件或自研的成本与风险。
3. 选出满足当前需求的**最简单可行方案**，解释不采用复杂方案的原因。
4. 定义数据模型、关键业务流程、权限、安全、错误处理和必要的非功能要求。
5. **先确认前后端 API 契约，再拆分前端与后端技术实现文档。**
6. 标出未知项、依赖项和实现风险；涉及重大不确定性时先做最小技术验证（Spike/PoC）。

### 6.3 《技术方案.md》建议结构

```markdown
# 技术方案
## 1. 设计目标与约束
## 2. 现有系统与可复用能力
## 3. 开源项目/组件调研与选型结论
## 4. 总体架构（按当前必要复杂度设计）
## 5. 数据模型与关键业务处理
## 6. API 契约、状态码与异常规范
## 7. 权限、安全与敏感数据保护
## 8. 前端技术方案与模块拆分
## 9. 后端技术方案与模块拆分
## 10. 测试策略与验收映射
## 11. 开发顺序、依赖与风险
## 12. 明确不做的设计
```

### 6.4 API 契约最低要求

前后端并行开发前，至少明确：

- 接口路径、请求方法、认证与权限要求；
- 请求参数的类型、必填性、默认值与校验规则；
- 响应字段、数据类型、空值定义及分页/排序规则（适用时）；
- 状态字段枚举、业务错误码、HTTP 状态码及错误文案约定；
- 幂等性、重复提交、超时、重试和并发处理要求（适用时）；
- API 版本或兼容策略及 Mock 示例。

**完成标准**：技术选型有可追溯依据，前后端依据同一份契约能够独立实现并验证，不依赖临时口头约定。

## 七、阶段 4：开发执行规范

### 7.1 前后端并行原则

前端依据 UI 文档与 API 契约开发页面、组件、交互、校验和异常反馈，必要时先使用 Mock 数据验证完整操作流程。

后端依据需求文档与 API 契约开发数据存储、权限校验、业务规则、接口与异常处理，并对关键逻辑编写测试。

双方可并行开发，但**不能分别自行修改同一接口定义**；需要变更时先统一修订契约，并同步通知和更新代码。

### 7.2 功能切片与开发节奏

建议以可独立验收的**纵向功能切片**为最小开发单元，而非一次完成所有页面、所有接口后再联调。

每个切片遵循：

```text
确认本次任务范围
   → 检查依赖与影响范围
   → 编写/修改代码
   → 执行本模块测试
   → 对照验收条件验证
   → Git 提交
   → 进入下一切片
```

一次任务尽量只解决一个明确问题；若 AI 发现额外问题，应列入待办并标明优先级，不得默认扩展范围。

### 7.3 AI 代码修改约束

1. 修改前先读取相关文件和既有约定，说明将改动的文件及影响范围。
2. 优先沿用现有目录结构、组件、函数及数据模型，不无故引入新框架或复杂设计模式。
3. 不修改无关代码，不擅自重命名对外字段，不破坏已确认接口和既有行为。
4. 不为未明确提出的未来功能增加插件化、微服务化、通用规则引擎等复杂能力。
5. 必须保留与风险匹配的输入校验、认证授权、错误处理、日志和敏感信息保护。
6. 对已有功能的修改要补充回归验证；验证失败不得宣称“已完成”。
7. 遇到文档冲突、无法验证的假设或重大技术风险，应列明阻塞点和建议方案。

### 7.4 Git 版本管理规范

- 初始化 Git 仓库并维护 `.gitignore`；密钥、令牌、私人配置不得进入版本库。
- 每个功能或修复以独立分支/可回滚提交管理，提交信息说明变更目的。
- 重要改动前保存稳定基线；合并前完成必要测试和代码检查。
- 避免 AI 在一个任务中混合大规模重构与新功能开发。
- 出现回归问题时优先定位相关提交，按影响最小的方式修复或回滚。

**完成标准**：代码能在目标环境运行，当前切片通过验收，相关测试可复现，变更有提交记录且具备回滚路径。

## 八、阶段 5：前后端联调、验收与安全检查

### 8.1 联调清单

- 前端请求与后端参数、返回结构一致；
- 状态枚举、错误码、空值和分页等规则一致；
- 主流程能从用户操作贯通到持久化结果及页面反馈；
- 异常请求、超时、网络错误、重复提交均有适当处理；
- 前端展示与实际业务规则、权限校验一致；
- 对失败的请求能够定位问题，不泄漏敏感错误信息。

### 8.2 功能验收

以《需求方案.md》中的验收条件为唯一产品行为基准，至少检查：

1. **主流程**：用户按预期路径完成核心任务。
2. **业务边界**：必填项、长度、范围、非法状态和重复操作。
3. **异常场景**：接口失败、无数据、网络中断、部分执行失败。
4. **权限场景**：无权限用户不可仅通过绕过前端限制而执行操作。
5. **回归场景**：此次修改未破坏已交付的重要功能。

### 8.3 最低安全基线（依风险调整）

- 后端进行身份认证、对象级权限与关键操作授权校验；
- 对外部输入进行校验，使用参数化查询等手段避免注入；
- 敏感数据和密钥不硬编码、不提交 Git、不写入不必要的日志；
- 对文件上传、外部 URL、第三方回调等高风险入口设定适当限制（如适用）；
- 生产环境关闭调试信息，配置必要的错误记录和访问控制；
- 对第三方依赖进行许可证和已知漏洞核查。

> 上述为通用基础检查，不代表已完成完整安全审计。涉及支付、隐私、重要业务数据等高风险场景时需进一步专项评估。

### 8.4 缺陷处理规则

发现缺陷时，先复现并确定预期与实际行为，再判断属于需求、UI、接口、前端还是后端问题。修复时遵循：**最小改动 → 定向测试 → 相关回归 → Git 提交**；避免让 AI 通过大范围重构解决局部 Bug。

**完成标准**：核心验收通过、阻断性缺陷关闭、必要安全检查通过、发布风险和已知限制已记录。

## 九、阶段 6：发布与迭代规范

发布前确认部署配置、数据库变更（如有）、依赖版本、环境变量、备份及回滚方案。发布后至少进行一次关键业务路径的冒烟测试，验证监控与错误日志可用。

每次迭代必须保留：版本号或 Git 提交、变更摘要、已验收功能、遗留问题、回滚方式和下轮待办。新需求优先从需求文档开始，不直接在旧代码中口头追加新规则。

## 十、需求、UI 与技术方案的变更控制

**统一规则：先判断变更性质，再更新受影响文档，最后修改代码。**

| 变更类别 | 首先更新 | 可能联动更新 | 验证重点 |
| --- | --- | --- | --- |
| 纯视觉 | UI 方案 | 前端样式 | 视觉、响应式、无业务回归 |
| 交互与表单 | UI 方案 | 需求规则、API 契约、测试 | 交互流程、校验、接口参数 |
| 业务规则 | 需求方案 | UI、技术、API、测试 | 状态流转、权限、业务结果 |
| API/数据结构 | API 契约及技术方案 | 前端、后端、迁移脚本、测试 | 兼容性、数据一致性 |
| 技术实现重构 | 技术方案（重大变更时） | 测试、发布说明 | 行为不变、性能与稳定性 |

每次变更建议记录：变更原因、变更范围、影响模块、受影响文档、风险、验证结果、对应 Git 提交。

## 十一、人和 AI 的职责边界

| 事项 | 人主要负责 | AI 主要负责 |
| --- | --- | --- |
| 需求 | 决定目标、范围和取舍，确认业务规则 | 拆解场景、发现遗漏、生成文档初稿 |
| UI | 确认体验、关键流程和最终方案 | 产出原型、交互建议、页面状态清单 |
| 技术选型 | 确认约束和风险接受范围 | 调研选项、比较成本、生成技术方案 |
| 编码 | 决定优先级、审核重要变更 | 按契约实现、测试并说明改动 |
| 测试与发布 | 判断验收结果、决定是否上线 | 生成并执行适用测试、定位缺陷、生成发布记录 |

**关键约束：AI 可以提出建议，但不得把未经确认的建议自动升级为需求、UI 定稿或技术决策。**

## 十二、可复用的 AI 开发总约束提示词

将以下内容放入项目级 AI 指令（例如 `AGENTS.md` 或所用工具对应的项目规则文件），并按具体项目补充技术栈与目录约定：

```text
你是本项目的 AI 软件开发助手，请严格遵守以下规则：

一、工作依据
1. 以已确认的需求方案、UI 方案、技术方案和 API 契约为主要实现依据。
2. 文档存在冲突、遗漏或歧义时，先指出并提出选择建议，不擅自补充业务规则。
3. 所有新增功能必须属于本期已确认范围。

二、设计与复用
4. 目标是以最小必要实现完成当前功能闭环，不为假设中的未来需求过度设计。
5. 优先复用现有代码、成熟组件和经验证可用且许可证兼容的开源能力。
6. 引入新依赖或架构前，说明必要性、替代方案、维护及安全风险。

三、编码与变更
7. 改动前先检查相关代码，列出准备修改的模块与影响范围。
8. 不修改无关逻辑，不擅自调整已确认的业务规则、API 契约或数据模型。
9. 每次实现一个可独立验证的功能切片，完成后执行相应测试再继续。
10. 重要改动应有明确 Git 提交，避免将无关重构混入功能开发。

四、质量与安全
11. 前后端严格遵循同一 API 契约，需变更时先更新契约并同步两端。
12. 必须保留必要的输入校验、身份认证、授权、异常处理和敏感数据保护。
13. 修复 Bug 时优先最小范围修改，并执行定向测试与相关回归测试。
14. 未实际执行的测试不得描述为“测试通过”；未验证的功能不得宣称完成。

五、交付说明
15. 每次任务完成时，说明：实现内容、修改文件、测试及结果、已知限制、待确认事项。
16. 发现明显超出需求范围的新想法时，单独列为建议，不立即实现。
```

## 十五、规范总结

**用需求文档约束“做什么”，用 UI 文档约束“怎么交互”，用技术方案约束“怎么实现”，用 API 契约支持前后端协作，用最小功能闭环控制复杂度，用测试与 Git 管理保证交付质量。**

整套流程的关键不是让 AI 产出尽可能多的文档和代码，而是让每一步都有明确的**输入、决策依据、输出与验收标准**，从而让开发可控、修改可追溯、成果可验证。
